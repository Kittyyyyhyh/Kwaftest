# 例会报告 W1：靶场样本有效性问题与蜜标方案

> 日期：2026-07-24 | 周期：第一周

---

## 一、问题提出

### 现象

初版样本在 WAF ON 下成功绕过并拿到了 flag：

```
;cat /flag.txt           → ✅ WAF放行, 拿到 flag{cmdi_l1_...}
UNION SELECT flag FROM flags → 🛡️ WAF拦截
```

### 追问

**这些样本有实际意义吗？**

WAF 放行 `cat /flag.txt` 不能证明 WAF 弱。因为：

- 现实中不存在叫 `flag.txt` 的目标文件
- `flags` 表名暴露了 CTF 靶场身份
- WAF 不放行的原因是：**它不认为读取一个叫 `flag.txt` 的文件是威胁**
- 如果把目标换成 `/etc/passwd` 或 `users.password`，结果可能完全不同

**结论：当前样本测试的是"WAF 对 CTF 玩具的检测能力"，不是对"真实攻击意图"的检测能力。**

---

## 二、核心矛盾

| 维度 | 需求 | 冲突 |
|------|------|------|
| 可验证性 | 需要一个唯一标记来确认攻击成功 | 这个标记不能出现在 payload 中（否则 WAF 不把它当威胁） |
| 真实性 | 攻击目标要模拟真实资产 | 但又不能是真的敏感文件（本地环境、安全约束） |
| 覆盖度 | 需要测多个攻击面 | 不能到处摆 flag（破坏真实性、维护复杂） |
| 归因 | 拦截发生时要知道拦了什么 | 语法、路径、编码三个变量混在一起无法区分 |

## 三、方案：嵌入式蜜标（Embedded Honeytoken）

### 3.1 核心思路

**验证标记只存在于目标中，payload 里不暴露任何靶场特征。**

```
Before:  payload="cat /flag.txt"        → WAF视角: 读一个不存在的测试文件
After:   payload="cat /app/config/db.php" → WAF视角: 读数据库配置文件

db.php 内容:
  define('DB_PASS', 'Kx9mP2vQ7wR3nJ5');  ← 像真实密码
  // deployment_id: hp-4f8a2c1b           ← 蜜标(嵌入注释，不破坏真实性)
```

- 蜜标格式：`hp-[0-9a-f]{8}`（8位hex，嵌入注释/配置值中）
- 验证方式：响应中正则匹配（Python 脚本 + PHP success-banner）
- 蜜标从不出现在攻击请求中

### 3.2 为什么不是随机 UUID？

- `hp-` 前缀在自然语言中极少出现，避免误匹配
- 8位 hex 足够唯一但体积小，可以嵌入到任何上下文
- 比 `flag{...}` 更像真实内部标记（deployment_id, access_key）

## 四、正交矩阵：技法 × 目标（三场景统一）

### 4.1 设计原理

**把"怎么打"和"打什么"拆成两个独立维度**，笛卡尔积生成样本，二维分析。

### 4.2 命令注入（CMDi）

```
                │ .env(凭证)   │ db.php(配置) │ app.log(日志) │ /etc/hostname(系统)
────────────────┼──────────────┼──────────────┼─────────────────┼──────────
;cat            │  测          │  测           │  测              │  测
|cat            │  测          │  测           │  测              │  测
||cat           │  测          │  测           │  测              │  测
$(cat)          │  测          │  测           │  测              │  测
`cat`           │  测          │  测           │  测              │  测
;cat${IFS}...   │  测          │  测           │  测              │  测
```

- 横轴：4档文件敏感度（蜜标嵌入对应文件）
- 纵轴：10+ 种注入语法
- 每个单元格 = 1 条样本，总基础样本 = 10×4 = 40 条

### 4.3 SQL 注入（SQLi）

```
                │ app_config(密钥) │ vip.access_key(凭证) │ users.email(PII) │ products.name(业务)
────────────────┼─────────────────┼─────────────────────┼──────────────────┼────────────
UNION SELECT    │  测              │  测                  │  测               │  测
UNION ALL       │  测              │  测                  │  测               │  测
/**/UNION       │  测              │  测                  │  测               │  测
/*!UNION*/      │  测              │  测                  │  测               │  测
extractvalue()  │  测              │  测                  │  测               │  测
CASE WHEN盲注   │  测              │  测                  │  测               │  测
```

- 横轴：4档数据敏感度（蜜标分散嵌入不同表和列）
- 纵轴：8+ 种注入语法
- 总基础样本 = 8×4 = 32 条

### 4.4 文件上传（Upload）

```
                │ .env          │ db.php        │ app.log
────────────────┼───────────────┼───────────────┼───────────
.php            │  测            │  测            │  测
.phtml/.php5    │  测            │  测            │  测
image/png MIME  │  测            │  测            │  测
GIF89a 头伪装   │  测            │  测            │  测
null byte 截断  │  测            │  测            │  测
条件竞争        │  测            │  测            │  测
```

- 横轴：3档目标文件（webshell 读取目标）
- 纵轴：6+ 种上传绕过技法
- 总基础样本 = 6×3 = 18 条

## 五、两阶段探测（降低成本）

### 5.1 问题

如果 WAF 在语法层面就拦截了某个分离符（如 `$()`），那用它去测试 4 种目标文件完全是浪费。需要先识别"WAF 拦的是语法还是目标"。

### 5.2 三角定位法

**两个不同无害目标，互相验证：**

```
探针:  ;id       → 🛡️ 被拦
探针:  ;env      → 🛡️ 被拦

两个不同命令都被拦 → 变量不是命令内容，是分隔符 ;
结论: ; 语法被 CRS 识别 → 跳过该语法的所有目标矩阵测试
```

**归因规则：**

```
if [(语法)A → 被拦] AND [(语法)B → 被拦]:
    拦的是语法 → skip 该语法的全矩阵
elif [(语法)A → 放行] AND [(语法)B → 放行]:
    语法干净 → 展开全矩阵测试
elif [(语法)A → 被拦] AND [(语法)B → 放行]:
    拦的是命令A本身 → 独立记录，不影响矩阵
```

### 5.3 探针设计

| 场景 | 探针A | 探针B | 无害原因 |
|------|-------|-------|---------|
| CMDi | `{语法}id` | `{语法}env` | 单命令，无参数，无文件路径 |
| SQLi | `{语法}1=1` | `{语法}2=2` | 无表名，无列名，无函数 |

**成本：** 10种CMDi语法×2 + 8种SQLi语法×2 = **36次探针**（秒级完成），结果缓存复用。

**节约：** 如果 60% 语法被拦（CRS PL4 典型），跳过对应目标矩阵，节省 60% 测试量。
